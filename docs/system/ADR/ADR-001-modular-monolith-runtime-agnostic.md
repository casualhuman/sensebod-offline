# ADR-001 — Modular monolith, runtime-agnostic (owner runtime: Node.js/Express)

**Status:** Accepted direction from the owner, 13 Nov 2026 (revision 2, OWNER-1). **This supersedes the v0.1/v0.2 proposal "Django 5.2 + gunicorn"**, which the owner rejected: *"we are not doing a django app … it's a node express. this is not for making specific backend tooling decision but tooling agnostics."*

**Decision.** One backend code base and one deployable, organised as modules (`core`, `identity`, `catalog`, `media`, `learners`, `exports`, `system`; SYSTEM-ARCHITECTURE §5), run as an HTTP process on `127.0.0.1:8000` behind the existing nginx, plus a worker process and timers from the same code base, all supervised by systemd. No containers, no broker. The owner's runtime is **Node.js with Express**. The architecture binds the backend to **requirements and mechanisms** (SYSTEM-ARCHITECTURE §4.1, R-1 … R-12), not to libraries: streaming request bodies to disk, an SQLite driver with WAL, `busy_timeout`, `BEGIN IMMEDIATE` and the online backup API or `VACUUM INTO`, serialized writes through one writer connection, a memory-hard password KDF (Argon2id or scrypt), numbered transactional SQL migrations, a systemd-supervised worker with one child process per job, an AE-2 zip writer, route-template logging, and a release that carries its own pinned runtime and dependencies. Node.js libraries named in this design (`better-sqlite3`, `node:crypto` scrypt, raw request streams or `busboy`, `child_process.fork`) are **examples only**.

**Context.** No backend exists. The frontend chose nginx for static files. Installs happen without internet; power cuts are frequent; the Pi has 8 GB and four cores; the team is small. The owner decided the runtime.

**Alternatives (recorded).** *Django/gunicorn* (the earlier proposal; superseded by the owner). *Go single binary* (small, simple deployment; not the owner's runtime). *Microservices / containers* (no independent deployables needed; image layers and an extra daemon on a microSD).

**Rationale.** A single process group is the smallest thing that serves the contract. Stating requirements instead of libraries keeps the verification meaningful whatever the backend engineer picks, and every requirement has a test that checks behaviour, not a name.

**Trade-offs.** Node.js-specific risks the backend engineer must manage: a synchronous SQLite driver blocks the event loop for the length of each query **and for the whole of any lock wait** (hence the short-transaction rule, snapshots for long reads, and the lock-wait rule R-3L); native modules must be built for `linux-arm64` and the bundled runtime's ABI (R-11); memory per process is an assumption until measured (SYSTEM-ARCHITECTURE §11.1, PERF-1). Uploads no longer hold a server thread per chunk (async I/O), but concurrent upload streams are still capped to bound file handles and disk I/O.

**Consequences.** Release bundles contain `runtime/` (pinned Node.js LTS linux-arm64 build), the backend and its installed dependencies; systemd units start `runtime/bin/node`; migrations are plain numbered SQL; the proofs of concept stay in Python because they test SQLite and filesystem behaviour, not the backend.

**Revisit when.** The owner changes the runtime, or PERF-1 shows the Node.js processes cannot meet the memory or latency budgets on the Pi.

**Revision 3 (13 Nov 2026).** V-026: lock waits are a Node-specific architectural rule, now binding as SYSTEM-ARCHITECTURE §4.1 **R-3L**. With a synchronous driver, `busy_timeout=5000` froze the whole process for 1,511 ms while another process held the lock for 1.5 s (Mac, `poc/poc_lock_wait.out`; the verifier measured 1,489 ms). Binding default (revision 3a): API `busy_timeout=0`, all writes through a single-flight write gate whose head retries asynchronously with backoff, ≤ 5 s per request from arrival, then `503 busy`; with 200 concurrent writes during a 1.5 s hold the loop lag was 6 ms, versus 1,521 ms for per-request retry with a 20 ms busy timeout (the revision-3 text, withdrawn). Allowed alternative: all API database access off the event loop (worker thread or writer process), where a 5 s `busy_timeout` is fine (measured 6 ms). Other writers follow the lock-hold budget R-3H. No `await` inside a transaction. Acceptance is test DB-6 (event-loop delay p99 < 50 ms, max < 200 ms under contention). V-028: `UV_THREADPOOL_SIZE` is set in the unit (e.g. 8), and the release self-check loads every native module on the Pi (P-1).
